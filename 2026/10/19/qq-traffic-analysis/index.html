流量分析

我是怎么把 QQ 的流量看明白的

先说结论

三个问题，我的答案先摆在这里，后面每一段都是怎么得出这个答案的过程。

问题 我的答案 关键证据
UDP 还是 TCP 两个都用，但分工完全不同 登录、消息走 TCP 长连接；语音、视频、部分近场发现走 UDP
加密还是明文 全链路加密，抓到的是密文 TLS 1.2 / 1.3 握手可见，应用层负载的香农熵接近 8 bit/byte
能否还原明文文件 默认不能；只在特定条件下能抠出文件头部特征 只有降级协商、自建中间人解密、或对方用了未加密通道时才可能

这个结论听起来很”标准答案”，但我第一次抓包时不是这么想的。下面按我当时实际的顺序讲。

我的环境

先交代清楚条件，不然结论没法复现。

  • 系统：Windows 11，抓包网卡选 WLAN（无线网卡），因为笔记本接的就是 Wi-Fi
  • 抓包工具：Wireshark 4.4
  • QQ 版本：QQ NT 桌面版（Windows），手机端 QQ 9.x（Android）
  • 账号：一个只在实验里用的测试号，好友只有一个同样是我自己的小号
  • 我抓的东西：登录过程、发一条文字消息、发一张图、一次语音通话

这里有个前置动作很容易被忽略：抓包前我把 Wireshark 的捕获过滤器留空，只设显示过滤器。因为捕获过滤器（capture filter）一写错，整段流量就漏了，而显示过滤器写错最多是看不见，重新过滤就行。这个选择后面救了我一次 —— 我原本只想抓 443，结果 QQ 有不少流量走 8080 和随机高端口。

第一遍：先不猜协议，先看端口

打开 Wireshark 抓 60 秒，登录 QQ，随便发一条消息，停止捕获。

第一件事不是找 UDP/TCP，而是「统计 → 端点」（Statistics → Endpoints）。这一步我想强调：别一上来就 tcp.port == 443，那等于先入为主。端点列表按包量排序，我看到的东西很杂：

  • 一堆到 443 的 TCP 连接，域名解析出来是 *.qq.com、*.gtimg.com
  • 到 8080 的 TCP，长连接，收发都持续有包
  • 若干 UDP 会话，端口在 8000-9000 区间跳动
  • 一些 UDP 的 5353 端口 —— 这是 mDNS，不是 QQ，是系统在发现局域网设备

接着「统计 → 协议分级」（Protocol Hierarchy）。TCP 占比最高，但 UDP 也不是零头。到这里我已经能回答一半了：如果作业问的是”UDP 还是 TCP”，那它其实是个陷阱题，答案是都要。

我第一次就踩了这个坑。我盯着 8080 那条长连接看了半天，认定”QQ 全走 TCP”，结果语音通话一开，UDP 流量哗一下上来，我整个人愣住了。所以后面我改成按”业务功能”分别抓。

第二遍：分业务抓，看每条线走什么

我重新抓了三段，每段只做一件事。

登录

登录时最明显的是 TCP 三次握手 + TLS 握手。用显示过滤器：

能看到 Client Hello，展开后 Handshake Protocol: Client Hello 里有 TLS 1.3、SNI 字段（服务器名）写着类似 *.qq.com 的域名、以及一大串 Cipher Suites。服务端回来的 Server Hello 会选一个套件。

这一步的结论很直接：登录通道是 TLS，也就是加密的。SNI 是明文的，这是 TLS 1.3 的 ECH 之外的正常现象 —— 也就是说，别人能看到你连了哪个域名，但看不到你登录用了什么密码、什么 token。

发一条文字消息

发消息时我用了 Follow → TCP Stream 跟 8080 那条连接。预期是看到我打的那句话，实际看到的是：

  • 一段段 16 字节整数倍的二进制
  • ASCII 侧栏（右侧的可读字符列）偶尔蹦出几个字母，也是无意义的
  • 换行、长度字段都像是规则的结构化头部

这里我用了一个量化判断：分组长度几乎全是 16 的整数倍。这是分组密码（AES 之类的块密码）在 GCM/CBC 模式下的典型特征 —— 明文被填充到块大小再加密。如果是明文 JSON 或者 protobuf，长度会是各种奇怪的数字。

语音通话

开语音后 UDP 立刻起来。Follow UDP Stream 看内容，全是固定间隔、固定大小的二进制包，长度在 100-200 字节之间跳。这个特征符合实时音频的编码帧（Opus 之类的编码器按帧输出），也可能是加密后的填充。

这一条线让我把答案敲定：QQ 的实时音视频走 UDP，因为它不能忍 TCP 的重传等待。丢一个包就丢一帧，用户听不出来；要是等 TCP 重传，就是明显的卡顿。

第三遍：怎么证明它真的加密了，而不是”看起来乱”

这是我花时间最多的一段，因为”乱码”不等于加密 —— 压缩过的数据也是乱码。

我用了四层证据，逐层递进：

  1. 协议标签。Wireshark 把这条流标成 TLSv1.2 或 TLSv1.3，说明它认出了握手过程。这是最外层、最省事的证据。
  2. ASCII 可读性。Follow Stream 右侧那列，如果是明文，能成段读出中文或英文；实际是一条断续的、毫无语义的字符带。
  3. 分组长度规律。统计长度分布，集中在 16 的倍数附近 —— 块密码特征。
  4. 香农熵。这是最硬的一条。我把流导出来算熵值：

结果：entropy ≈ 7.99 bit/byte。

对比一下参考值：普通英文文本大约 4.5，压缩包大约 7.9-8.0，随机数据接近 8.0。熵到这个数，基本可以排除”未加密”的可能。

这里我犯过一次错：一开始我拿一条只有 200 字节的流去算，熵算出来 7.2，我还挺得意地说”看，加密的”。后来才知道小样本的熵天然偏低，因为符号还没凑齐。样本量至少几 KB 才有意义，我把流攒到 50 KB 以上再算，才是 7.99。

第四遍：文件还原，能还是不能

作业第三问是”恢复可能为明文传输的文件，不同文件有不同头部可作为特征码”。我的答案分两层。

理论上：靠 Magic Number 定位

不同文件格式有固定的头部字节，这就是特征码：

格式 十六进制头部 ASCII 侧栏
JPEG FF D8 FF ÿØÿ
PNG 89 50 4E 47 0D 0A 1A 0A .PNG....
PDF 25 50 44 46 %PDF
ZIP / docx 50 4B 03 04 PK..
GIF 47 49 46 38 GIF8

在 Wireshark 里可以用 Ctrl + F，搜索类型选「分组字节」（Packet bytes），再选「十六进制值」，输入 ffd8ff 去搜。如果这条流是明文传输的图片，搜到之后从那个位置往后跟，直到 FF D9（JPEG 结束标记），把这段字节 Export Selected Packet Bytes 存下来，就是一张能打开的图。

实际上：这次一条都捞不到

我按上面的方法试了。搜 ffd8ff：零命中。搜 25504446（%PDF）：零命中。搜 504b0304：命中了几次，但展开一看是 TLS 握手里的会话票据，不是文件。

原因很明确：文件在传输前已经被加密了，特征码也跟着一起被加密了。特征码不在密文里，就像把信锁进箱子后，凭信封上的字认不出里面写了什么。

所以第三个问题的诚实答案是：在当前版本的 QQ 上，用常规抓包手段恢复不出明文文件。作业里说的”不同文件有不同头部作为特征码”这个知识点是对的，但它成立的前提是那条传输通道没有加密，比如：

  • 老式 HTTP 上传（http.request.method == "POST" 里直接就是文件字节）
  • FTP 传输
  • 未加密的局域网文件互传
  • 自己搭的测试环境，用 HTTP 走一遍上传流程

我给自己的补充实验是：在本地起一个 python -m http.server，从浏览器下载一张图，抓这个流量，再用 ffd8ff 去搜，一次就搜到了，把字节导出来能正常打开。这一步是为了验证”我掌握了方法”，而不是为了证明”我能解 QQ 的密文”——这两件事不是一回事。

我踩过的坑

按时间顺序列，都是真踩过的。

坑一：以为 UDP 就是”没加密的”。实际 QQ 的 UDP 音视频也是加密的，加密和应用层用什么传输协议是两件独立的事。TCP/UDP 决定怎么送，加密决定送的什么。

坑二：抓包网卡选错。一开始选了个 Loopback 或者已断开的虚拟网卡，抓了半天一条 QQ 的包都没有。后来看「捕获 → 选项」里哪块网卡有流量曲线，才选对。

坑三：忘了关系统代理。开着代理抓包，看到的全是到代理服务器的一条 TLS，看不到后面分几路，容易得出”只有一个连接”的错误结论。

坑四：用小样本算熵。前面提过，200 字节算出 7.2 就下结论，属于自欺欺人。

坑五：把 mDNS 当成 QQ 的流量。5353 端口的 UDP 是系统在发现打印机和电视，跟 QQ 无关。判断归属要看进程和域名，不能只看端口活跃度。

关于”保护个人隐私”，我做了这些

这部分是我写这篇文章时最在意的。作业要求发布到 blog 并保护隐私，我的处理清单如下：

  • 账号信息：所有 QQ 号、UIN、手机号、IMEI 一律打码，只保留位数
  • IP 地址：内网地址换成 192.168.1.x，公网 IP 段后两段用 x.x 代替 —— 公网 IP 能定位到城市甚至小区，等于半个家庭住址
  • 域名：保留 *.qq.com 这种通配写法，把具体子域名（尤其带个性化字段的 CDN 域名）抹掉
  • 好友昵称、群名：全部替换成 好友A、测试群
  • 截图：用 Wireshark 之前先关掉”解析名称”（View → Name Resolution 全关），否则可能把内网主机名解析出来
  • pcap 文件：不直接上传原始 pcapng。要分享就用 editcap 裁剪，只留目标会话，并且先检查有没有意外带上的其他流量：

我最后没有上传 pcap。理由很简单：一份完整的抓包文件里，除了 QQ 的流量，还有你同时开着的所有网页、所有后台同步。裁剪也很难保证干净。所以我只放截图和命令行输出。

我的想法

做完这一轮，我最大的感受不是”QQ 加密很强”，而是我以前对”加密”的理解太粗。

以前我的模型是”加密 = 看不懂”。现在我知道加密至少分几层：传输层加密（TLS）保护的是这一跳，应用层端到端加密保护的是这两端，两者可以叠加，也可以只有一层。同一条流量里，SNI 是明的、证书是明的、包长是明的，加密从来不等于”什么都看不到”。流量分析的很多结论恰恰来自这些”明着的地方”——你连了谁、什么时候连的、传了多大的东西。

第二个感受是关于方法的。我原来抓包的习惯是”想到什么就过滤什么”，现在会先做端点和协议统计。先把地图画出来，再决定往哪走，比一头扎进过滤器里高效得多。

第三个感受，是关于诚实的。作业第三问很容易写成一个”演示我能还原文件”的漂亮答案，但实际在 QQ 上还原不出来。我选择把”还原不出来”和”为什么还原不出来”写清楚，再补一个本地 HTTP 的实验证明方法本身是掌握的。承认边界，比假装全能更接近真实的安全工作。
