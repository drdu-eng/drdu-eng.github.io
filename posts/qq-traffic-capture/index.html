QQ 流量抓包

发表于2026-10-20|更新于2026-10-20|学习笔记
|浏览量:

结论先行

作业三个问题，我先把自己实际抓出来的答案放在最前面：

题目 我的结论 关键证据
一：UDP 还是 TCP 消息通道走 TCP（8080 长连接 + 443 的 TLS），UDP 只承担辅助角色 netstat -ano 显示 QQ 进程的多条 ESTABLISHED TCP 连接；抓包中 443 与 8080 全是 TCP 会话
二：加密还是明文 载荷加密，协议头明文。443 端口是标准 TLSv1.3，8080 端口是 QQ 私有二进制协议（头部标识明文、内容密文） Wireshark 抓到 TLSv1.3 Application Data；8080 流里看到 Heartbeat.A live 明文头 + 高熵载荷
三：能否还原明文文件 当前版本还原不出。特征码搜索的前提是传输未加密，而 QQ 全链路加密 方法本身用特征码表 + 对照实验验证（见文末）

下面按我实际操作的顺序讲，五张截图对应五个关键节点，每一步都写了”我当时在想什么、看到了什么、得出了什么”。

第一步：先找到 QQ 的进程，别急着开 Wireshark

我一开始犯的错误是：打开 Wireshark 就开始抓，结果抓到几百个包，根本分不清哪个是 QQ 的、哪个是系统后台在偷偷跑的。

后来想明白了：得先知道 QQ 是谁，才能在流量里认出它。所以第一步不是抓包，而是查进程。

在 PowerShell 里执行：

可以看到 QQ 主进程的 PID 是 12004（其余几个 QQGuild 是 QQ 频道相关子进程）。记住这个数字，它就是接下来在连接表里”认人”的凭证。

这一步的教训：作业里很多时间浪费在”抓了一堆包但不知道是谁的”上。先定位进程，再抓包，顺序不能反。

第二步：反查 QQ 的连接（回答题目一：UDP 还是 TCP）

拿着 PID 12004 去连接表里查：

这张图信息量很大，我逐行读给大家看。

先看 TCP 部分：

  • 10.205.245.29:56484 → 120.232.130.121:8080，状态 ESTABLISHED —— 这就是 QQ 的消息长连接，8080 端口，已建立、正在通信
  • 大量 → xxx:443 的连接，状态多是 CLOSE_WAIT —— 这些是 HTTPS 连接，一方已经关闭、另一方还在收尾。CLOSE_WAIT 多说明 QQ 频繁地建立和断开 HTTPS 短连接（拉取头像、表情、配置之类）
  • 还能看到 IPv6 的连接（方括号那种 2409:895c:... 地址），说明 QQ 是 IPv4/IPv6 双栈都在用

再看 UDP 部分：

  • 0.0.0.0:4019、127.0.0.1:57306 这类条目 —— QQ 确实开了 UDP 端口，但注意它们没有远端地址（*:*），说明只是绑定了端口在监听，并没有持续地对外通信

所以我回答题目一的思路是：

  1. 消息发送走的通道，在连接表里是 TCP:8080 的 ESTABLISHED 长连接
  2. UDP 端口存在但没有活跃会话，它的用途（音视频、局域网发现）在纯文字消息场景下不参与
  3. 结论：发消息 = TCP。UDP 在 QQ 架构里有位置，但不在这条链路上

这里有个容易踩的坑：netstat 里那些 UDP 条目容易让人兴奋地写”QQ 走 UDP”。但**”绑定了端口”和”正在用它通信”是两回事**，要看远端地址是否存在。

第三步：开 Wireshark 验证——先看 443 端口的 TLS 流量

定位完连接，接下来打开 Wireshark 抓包，用过滤器逐条验证。

先过滤消息相关的 IP。我用的是：

这张图里我能确认几件事：

  1. 协议标签是 TLSv1.3——Wireshark 完整解析出了握手过程：Client Hello（371 字节）→ Server Hello, Change Cipher Spec → Application Data
  2. SNI 字段是明文的，写着 msg.qzone.qq.com——这说明虽然内容加密，但”我在访问哪个服务”这件事是公开写在握手包里的
  3. 有意思的是，同一个 IP 既开着 443（TLS），也开着 8080（私有协议），QQ 把不同业务分流到不同端口
  4. 列表里还能看到 TCP Retransmission（红色）和 [TCP Previous segment not captured]——这是网络抖动造成的正常现象，抓包时不用慌，不是抓错了

SNI 是明文这件事值得单独说一句：加密保护的是”说了什么”，不保护”在跟谁说”。SNI、包长、时间戳都是明文的，这就是流量分析（而非内容解密）能做的事。

第四步：443 端口的另一面——遥测与心跳

换一个维度看，直接过滤 443 端口的所有流量：

这张图和上一张对比着看很有意思：

  1. Client Hello (SNI: sNlQzpta1emetry.tencent.com) —— 这是 QQ 的遥测上报（telemetry = 遥测），QQ 在悄悄向腾讯汇报运行数据。它和消息无关，但占用了 443 的会话数
  2. 大量 TCP Keep-Alive，Len=0 或 1 —— 这是连接保活心跳，纯粹告诉对方”我还在”，不带任何业务数据。千万别把 Keep-Alive 当成消息
  3. Application Data（Len=246、105、109 等）—— 这些是加密后的业务数据，消息内容就藏在这类包里，但已经无法从内容分辨

我在这张图上犯过一次误判：一开始看到包很多很活跃，以为消息流量很大。后来意识到大部分是遥测和保活，真正的消息只在发送瞬间出现一两个包。“包多”不等于”有消息”，这个直觉必须纠正。

第五步：8080 端口——最有意思的发现

前面 netstat 已经确认消息长连接在 8080，来看它的真面目：

这张图是我整个实验里最有收获的一张。

看底部的 Hex Dump 面板（右侧 ASCII 列）：能清楚看到 Head 和 Heartbeat.A live 这样的明文字符串！

这说明 8080 端口上跑的是 QQ 自家的二进制私有协议，不是标准 TLS：

  • 协议头是明文的：Head 是包头标识，Heartbeat.A live 是心跳标记——客户端和服务器靠这些字符串互相确认”这是什么类型的包”
  • 载荷是加密的：除了这几个标识，其余内容全是高熵的二进制乱码

逐个认一下这张图里的包：

包号 类型 判断依据
899 本地回环通信 127.0.0.1 起止，Len=53，是本机进程间的小包
928 心跳包 Len=74，Hex 里有 Heartbeat.A live
929 纯 ACK 确认 Len=0，不带数据
1381 连接正常关闭 FIN, ACK，一方说”我说完了”
1417（红色） 重传 Retransmission，网络抖动导致的重复包

那我的消息长什么样？ 和心跳包长得几乎一样——同样是 [PSH, ACK]、同样的二进制头结构——只是 Len 会大得多（一条 120 字节的消息，加上协议头和加密填充后约 200~300 字节）。因为内容加密了，没法从内容上区分”这是消息还是别的”，只能靠发送时刻的时间戳去定位。

题目二汇总：四条证据确认加密

把前面四步的观察整理成证据链：

# 证据 观察结果 来源截图
1 协议标签 Wireshark 解析出完整的 TLSv1.3 握手 图 3
2 SNI 明文 msg.qzone.qq.com 可读，说明在 TLS 隧道内 图 3
3 443 无法读 Application Data 全部无法展示语义 图 4
4 8080 私有协议 协议头明文（Head/Heartbeat），载荷密文 图 5

结论：QQ 消息传输全链路加密。443 走标准 TLSv1.3，8080 走”明文协议头 + 加密载荷”的私有协议。无论是哪种，消息内容都无法从抓包中直接读出。

补一个量化手段（如果需要更硬的证据）：把追踪流导出成二进制文件，计算香农熵——明文约 4.5 bit/byte，加密数据约 7.99。我用脚本实测加密流，结果 7.99，逼近理论上限 8.0。

题目三：文件还原——方法有效，但 QQ 不给机会

第三问要求”恢复可能为明文传输的文件，不同文件有不同的头部作为特征码”。

方法本身（这是要掌握的）

不同文件格式的开头有固定的字节序列，叫文件头特征码（Magic Number）：

格式 特征码（十六进制） ASCII 侧显示
JPEG FF D8 FF ÿØÿ
PNG 89 50 4E 47 0D 0A 1A 0A .PNG....
PDF 25 50 44 46 %PDF
ZIP / docx 50 4B 03 04 PK..

在 Wireshark 里按 Ctrl + F，搜索方式选**「分组字节」+「十六进制值」**，输入 ffd8ff，就能在流量里定位 JPEG 文件的起点；找到后从那个字节开始，一直到 FF D9（JPEG 结束标记），把中间的字节导出来就是完整图片。

为什么在 QQ 上行不通

上面的抓包已经给出了答案：QQ 全链路加密。

文件在进入网络之前就被加密了，特征码 FF D8 FF 也一起被加密成了一串随机字节。在密文里搜明文特征码，就像对着上了锁的箱子找信封上的邮编——方法没错，但对象错了。

怎么证明”方法有效”（对照实验）

为了说明不是我不会，而是 QQ 不给机会，我设计了一组对照：同一网络下，用明文 HTTP 传同一张图。

浏览器访问 http://127.0.0.1:8000/b.jpg，同时用 Wireshark 抓包。在这份流量里搜 ffd8ff，一次命中；追踪流 → 原始数据 → 导出保存，图片可以正常打开。

两边对比的结论：

HTTP 对照组 QQ 实验组
特征码搜索 命中 零命中
文件导出 成功，可打开 不适用（无起点可导）
原因 传输未加密 传输全程加密

所以题目三的完整回答是：特征码还原方法成立，但成立前提是传输通道未加密；QQ 当前版本全链路加密，前提不成立，因此无法还原。 这个”不能”是方法边界问题，不是能力问题。

踩坑记录

坑一：一上来就抓包，抓了几百个包不认识。
后来才明白应该先 Get-Process 定位 PID，再 netstat 反查连接，最后才开 Wireshark。顺序反了事倍功半。

坑二：把 Keep-Alive 当成消息。
443 端口里大量 TCP Keep-Alive（Len=0/1）让我以为流量很活跃。其实那只是保活心跳，真正的消息只在发送瞬间出现。

坑三：看到 UDP 条目就写”QQ 走 UDP”。
netstat 里 UDP 只有本地端口没有远端地址，说明只是绑定了端口在监听，并没有在消息场景下通信。”绑定端口”和”用它通信”是两回事。

坑四：被红色包吓到。
Retransmission、RST 这些红色包看着吓人，其实都是 TCP 的正常机制：重传是网络抖动，RST 是强制断开。不影响分析。

关于隐私的说明

  • 本次抓包全部发生在我自己控制的设备和账号之间，未涉及任何第三方通信
  • 截图中的 10.205.245.29 是我的内网地址（10/8 私有网段），120.232.x.x、112.49.x.x 等是腾讯服务器地址，不涉及个人定位
  • 唯一需要提醒自己的：截图里的 IPv6 地址（2409:...）是全球可路由的，如果要发布到公网，应当打码。作业场景下保留，公开传播前务必处理
  • 好友昵称、群名等未出现在截图中

写在最后

这次实验最大的收获不是”学会了抓包”，而是理解了一个范式：

加密保护的是内容，不保护行为。

我看不到消息说了什么，但我能看到：消息什么时候发的、发给了哪个服务器、发了多大、用了什么协议、连接保持了多久。这些”元数据”全部是明文的，而流量分析的价值恰恰从这里开始。

等保 2.0 讲”一个中心、三重防护”，其实流量分析也是这个思路：不攻破加密这个”中心”，而是从通信网络、区域边界、计算环境三个维度收集证据。两门课在这里接上了。
